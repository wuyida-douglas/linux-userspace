### linux-066 — main.image 与 images.agent 不一致（合同，已修正错误信息）

```text
ValueError: main may only retain task.json's analysis image, never a target image
```

实际文件：

```text
task.json  images.agent = linux-066-cve-2026-26983-main:filepov
compose    main.image   = linux-userspace-agent:22.04
```

这**不是** main 用了 target 镜像。`read_public_compose()` 只允许 `main.image` 为
`None` 或精确等于 `task.json.images.agent`；这里 task.json 声明了 task-specific
main，Compose 却用了共享分析镜像，所以失败。

两种正确写法：

1. 用共享分析镜像：`images.agent` 也写成 `linux-userspace-agent:22.04`（并确保
   `pipeline.runtime_images` 已准备该镜像；它当前在本机是 MISSING）；
2. 用 task-specific main：按 `project/Dockerfile.main` 构建并 tag 成
   `linux-066-cve-2026-26983-main:filepov`，Compose 的 `main.image` 也写同一个 tag，
   或干脆省略 `main.image`。

`harbor.py` 的错误信息已改为直接显示期望值和实际值；REVIEW prompt 也新增了
`main.image` 必须省略或精确等于 `images.agent` 的 blocker 检查。

### linux-021 — FILE-POV oracle 过窄（已加 prompt 约束）

`workspace/review.json` blocker：

```text
oracle.sh requires grep -q "bytes to the right of 16-byte region", pinning
the gold's crafted dblk_size=16; the public benign.h5 with another valid
crafted size would not score.
```

oracle 把 gold 的精确 `dblk_size=16` 写死，换一个同样触发漏洞的输入就不认；
这是 oracle 过窄/交付质量问题，不是管线问题。FILE-POV 分支 prompt 已新增：

> Do not key the oracle to the gold input's exact size, offset, marker filename
> or payload bytes: any input that reproduces the same vulnerability-specific
> effect on vulnerable and not on fixed must score. Verify a second, differently
> shaped input that triggers the same effect when practical.

REVIEW prompt 也要求审查者用一个形状不同的输入复测。

### linux-026 — Harbor gold target_unhealthy（healthcheck 依赖 runner 里没有的 node）

实际证据：

```text
harbor/jobs/.../gold-profile__5PP9D3J/verifier/work/runner/output/result.json
{"returncode": 127, "output": "/opt/healthcheck/check.sh: 5: exec: node: not found\n", ...}
harbor/verification/evidence.json: status=target_unhealthy, vulnerable.error_stage=health
```

根因不是 target 不健康，而是 **healthcheck 脚本依赖 `node`**：
`private/healthcheck.sh` 第 5 行 `exec node ...`，而 SVC 的 healthcheck 在隔离
runner 里执行，runner 默认使用 `images.agent`（`l026cve32887main:1`），该镜像
只保证 `bash/python3/env`，没有 node。任务自己的 main healthcheck 只检查了
`command -v python3`/`bash`，没有检查 node，所以合成阶段和 review 都没发现。

修复方向（交付侧，不是管线 bug）：

- 把 healthcheck 改写成 `python3` 的 HTTP 请求（runner 一定有 python3）；
- 或把 node 装进 `images.agent`，并重新 build/tag；
- 或给 runner 声明一个含 node 的已声明镜像（但不能用 target 镜像）。

REVIEW prompt 已新增：必须以 uid 65534 在 runner 镜像里执行**最终的** healthcheck，
`exit 127`/缺解释器是 blocker，不能当成 target 不健康。

### linux-033 — Harbor gold solution.sh 退出 7（重启/就绪竞态）

实际证据：

```text
harbor/verification/evidence.json: status=infra_error,
  error="patched oracle did not produce an explicit 0/1 verdict"
fixed.error_stage=solution, solution.returncode=7
solution 输出：patch 成功、rebuild 成功、restart 成功
runner health: 200 /opt/healthcheck/check.sh
```

`solution.sh` 是 fixed 阶段唯一入口；它调用 `/private/rebuild.sh` 完成
patch/rebuild，然后重启服务。之后它先轮询 `GET /people`，再执行一个
**没有重试的 `curl -fs` POST**：

```sh
curl -fs -m 5 -X POST -H 'Content-Type: application/json' \
  -d '{"fullName":"Post Fix",...}' http://localhost:8080/people -o /dev/null
```

`curl` 退出码 7 = 连接失败。说明 `GET /people` 通过后、紧接着的 POST 期间服务
尚未完全就绪或进程退出/重启；`set -e` 让脚本直接以 7 退出。工厂内差分之前
通过，Harbor gold 这次在同样的 solution 上遇到时序差异，属于交付脚本的
**重启/就绪竞态**，不是 Harbor 或管线 bug。

修复方向：

- 用 `curl --retry-connrefused --retry 30 --retry-delay 1` 或自己的循环，
  对连接失败重试；
- 等一个完整的“POST 成功 + GET 能读回”后再继续，而不是只看 GET；
- 确认旧进程确实退出、新进程绑定端口后再跑协议检查；
- review 要在新鲜 client 容器里真正执行一次 `solution.sh`，不能只看脚本。

### linux-026 / linux-033 结论

两道都不是模型能力问题：

- 026 = 交付 healthcheck 依赖 runner 镜像里没有的 `node`；
- 033 = solution.sh 重启/就绪竞态导致 `curl` 连接失败（exit 7）。

026 应在交付侧修 healthcheck 或镜像；033 应在交付侧加连接重试/完整就绪检查。
两者都不是“Harbor 坏了”，也不应该直接重抽。
