# Pipeline iteration report — iterate-20261109-01 / batch 001

## 结论

第一批 30 题没有达到可用产出：23 题进入终态，其中 **17 题是管线问题**，6 题是模型/题目能力问题；另有 7 题在 routing/synthesis 长时间无进展，被人工终止。失败率 100%，已按 70% 阈值停止本 run。

这不是模型能力不够为主，而是两个**确定性的管线 bug**导致的批量失败：

1. 当前 Docker 29 使用 containerd image store，`docker save` 产出 OCI 归档；`docker load` **从 stdin 读取**时报 `unrecognized image format`，但 `docker load -i <file>` 可以正常加载。11 道题因此卡在导出后的归档重载。
2. 合成 Agent 常省略 `runner.health_timeout_sec`（4 题）或写 `restart_command: null`（2 题），合同校验直接拒绝，任务在 freeze 前失败。

## 逐项证据

### A. OCI 归档无法从 stdin 加载（11 题）

受影响：

```text
linux-006 linux-008 linux-010 linux-013 linux-016 linux-019 linux-021
linux-025 linux-026 linux-027 linux-028
```

错误：

```text
RuntimeError: cannot load .../images/target.tar.gz: unrecognized image format
```

复现：

```bash
gzip -dc target.tar.gz | docker load          # unrecognized image format
docker load -i target.tar.gz                  # Loaded image: ...
```

`docker save` 归档同时包含 OCI `index.json` / `blobs/` 和 Docker `manifest.json`，stdin 路径无法识别。根因在 `pipeline/harbor.py` 的 `load_archives()` 和随包 `bin/load_image.py` / `bin/load_shared_images.py`。

修复：所有加载改为 `docker load -i <archive>`。

### B. task.json 默认字段缺失（6 题）

```text
linux-002 / linux-030 / linux-032 / linux-033:
  ValueError: runner.health_timeout_sec must be an integer in 1..3600
linux-031 / linux-037:
  ValueError: restart_command must be a string array
```

这些不是安全性问题，而是可规范化字段：

- `runner.health_timeout_sec` 缺失时默认等于 `runner.timeout_sec`；
- 显式 `restart_command: null` 规范化为 `[]`；
- 缺省 `restart_command` 本来就被合同接受。

修复：`pipeline/task_contract.py:normalize_declared_metadata()` 增加上述默认值，并记录 repair；审查需要重新确认。

### C. 模型/题目能力问题（6 题）

```text
linux-007 / linux-020: synthesis_blocked（模型用实验证明路线不可做，见 failure.json）
linux-017: review_rejected（独立审查发现 oracle 可伪造）
linux-018 / linux-024: not_suitable（路由拒绝）
```

这些不作为管线 bug 携带；其中 `synthesis_blocked`/`not_suitable` 是候选人终态，`review_rejected` 是题目质量问题。

### C2. gateway 504（1 题）

`linux-022` 的 `synthesis/result.json` 是：

```text
API Error: 504 upstream request timed out
elapsed_sec: 3446.27, num_turns: 11
```

这是模型网关超时，不是模型能力。已把“`synthesis_incomplete`/`agent_error` 且错误文本含
504/upstream request timed out”也纳入 `--carry-failed` 的管线携带集合。

### D. 人工终止的 7 题：Claude Code 在 result 后挂起

```text
linux-003 linux-005 linux-011 linux-015 linux-023 linux-029 linux-034
```

根因不是模型没有工作，而是 `pipeline/agent.py` 只通过 `process.wait(timeout=18000)` 等
Claude Code CLI 退出，退出后才把 `stdout.jsonl` 复制成 `trajectory.jsonl`。这批
任务使用 `claude` 执行器，CLI 已经输出了最终 `type=result`，但进程继续挂起：

| 任务 | result 事件 | 结论 |
| --- | --- | --- |
| linux-003 / 005 / 023 / 029 | `is_error=false`, `subtype=success` | 实际已完成，进程未退出 |
| linux-011 / 015 | `is_error=true`, `subtype=error_max_turns`, 301 turns | 模型预算耗尽 |
| linux-034 | `is_error=false`，进程正常退出 | 已完成 |

因为 `synthesis/result.json` 一直停在 `running`、`trajectory.jsonl` 为 0，supervisor
误判为“没有 turn 进展”。`stderr.txt` 里的 `unrecognized_model glm-5.3` 只是 CLI
本地模型目录的警告，不是挂起原因。

修复：`agent.run()` 每 2 秒检查 `stdout.jsonl`，看到 `type=result` 后主动终止整个
进程组，并按 result 的 `is_error` 标记 `completed` / `agent_error`；不再等 5 小时
超时。新增 `tests/test_agent_watchdog.py` 覆盖“结果已出但进程继续 sleep”的场景。
4 个实际成功的任务可以重新进入 review/Harbor，或在下一次 fresh 选择中重跑。
