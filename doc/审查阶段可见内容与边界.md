# 审查阶段：Agent 能看到什么、可以做什么

> 适用版本：`/nvme/wuyida/新管线开发` 当前工作区，2026-11-10。
> 审查发生在合成完成、`frozen_delivery` 通过之后，Harbor 验收之前。
> 本文说明审查 Agent 的实际可见范围、三个分支各自的检查重点，以及
> “审查阶段改交付”为什么会被拒绝。

---

## 1. 审查是一个全新 Claude Code 会话

控制器用 `pipeline/agent.py` 启动一个**全新的** `claude -p` 会话：

```text
cwd = results/<run>/<task>/workspace
model = 合成阶段同一个模型
prompt = pipeline/prompts.py 的 REVIEW
```

它不继承合成会话的上下文，工作区里初始呈现为：

```text
workspace/
├── input/                  # 不可变输入：meta.json、src/、fix.diff、alternate-candidates.json
├── route.json              # 路由决定
├── delivery/               # 合成产物（真实交付；task.json 由控制器生成）
├── review-input/           # 审查证据快照
│   ├── live.chat.md        # 完整合成轨迹（含 thinking/工具/压缩边界）
│   ├── tool-calls.jsonl    # 工具调用索引，北京时间
│   ├── tool-logs/          # 合成工具日志（如果存在）
│   └── fix.diff            # 原始修复 diff
└── NETWORK.md
```

`review-input/` 是控制器在审查前从 `output/synthesis/` 和 `input/` 复制的**证据快照**
（轨迹、工具调用、fix.diff），不包含 `delivery/`。交付本体就在 `delivery/`，审查
Agent 直接读它；控制器在审查前后用哈希清单确认它没被改动。最后只在 workspace 根
写一个 `review.json`。

`cwd` 设为 workspace 只决定相对路径和 `review.json` 的落点，不是沙箱。

合成阶段的重建证据不只在 `review-input/`：`../synthesis/stdout.jsonl` 是完整原始
stream，`stderr.txt` / `cli-debug.log` 保留错误和 Claude Code 调试信息，
`background/` 保存后台命令输出。Autocompact 产生的 `compact_boundary` 和
`isCompactSummary` 会作为事件保留在 `live.chat.md` / `sft.jsonl`，压缩前的事件
不会删除。

## 2. 实际上它能“看到”什么

审查 Agent 是宿主机上的进程，不是容器沙箱。技术上它可以：

- 读整个 `workspace/`，包括 `input/`、`route.json`、`delivery/`、`review-input/`；
- 读 `../synthesis/`（`live.chat.md`、`tool-calls.jsonl`、`sft.jsonl` 等）；
- 使用宿主 Docker 查看镜像、启动临时容器、执行命令；
- 读写宿主机文件系统（以当前用户权限）。

但合同把它限制为**只读审查**：

- 不修改 `delivery/`；
- 不跑完整的私有差分（Harbor/final verifier 才做）；
- 只把结论写入 `workspace/review.json`。

所以文档里说“它拿到 review-input”，指的是**提供给它的证据包**，不是
“它只能看到这些”。读范围没有技术边界，只有 prompt 的只读纪律；控制器的
哈希检查只能保证 `delivery/` 没被改，不能阻止它读取宿主机上的其它文件。

## 3. 三个分支分别要审查什么

### 3.1 共同检查（所有分支）

- `delivery/task.json` 由控制器在审查前生成，**不是合成 Agent 手写**；审查只核对
  它和 `route.json`、公开 Compose、固定脚本是否一致，不要求合成轨迹里出现过
  “写 task.json”；
- **instruction 陈述真实性**：instruction.md 声称的源码/工具路径、端点、提交类型
  和大小限制必须在 main 与公开环境中真实存在或按陈述工作；只检查陈述是否属实，
  不因为披露了 hash/salt/用户名/凭据等信息就拒绝；
- 如果 instruction 说某条捷径“不生效”（例如直连端点或良性输入），要验证它在
  交付的 main/镜像里确实被挡住；如果随带的凭据/配置让这条被声称不生效的路径
  生效，是 suitability failure；
- 如果 instruction 说必须构造 CVE 专属输入，检查普通/良性输入是否已经满足
  声明的 vulnerable 效果；如果普通输入就满足，任务不是 CVE 专属的，必须拒绝；
- instruction 的提交类型、大小限制、端点和工具必须与 runner/oracle 一致；
  隐藏的更严格限制、不同路径或未公开端点导致合法解失败，是 suitability failure；
- `task.json` 与 `route.json` 的 `branch` / `host_type` 一致；
- `images.agent` / `images.target` 是不同、可导出的 prebuilt tag；
- `runner.image` 必须为 `null`；runner 不是第三个镜像，而是 verifier 新建的
  独立容器，固定使用 `images.agent`；
- 公开 Compose 的 `main.image` 必须省略，或**精确等于** `task.json.images.agent`；
  写成共享 `linux-userspace-agent:22.04` 但 `images.agent` 是另一个 tag，也是 blocker；
- 公开 Compose 只有 `main` + `client`（+ 真实 sidecar），没有 `runner`、`ports`、`build`、`privileged`、私有 bind；
- `main` 是分析工作站，不含已构建的漏洞程序；`client` 才是 target；
- `private/healthcheck.sh`、`oracle.sh`、`solution.sh`、`gold/*` 存在且语义正确；
- 必须在 **runner 容器**（独立容器，固定使用 `images.agent`）里以 uid 65534
  执行**最终的** healthcheck；`exit 127` 或缺少解释器/工具是 blocker，不是
  target 不健康；
- `oracle.sh` 只允许 exit 0/1；0 = 效果存在，1 = 明确不存在，其他 = verifier 错误；
- `solution.sh` 应用真实官方修复，编译型漏洞必须离线重建并替换实际运行的 binary/library；
- 合成轨迹只是线索，不能替代独立验证；
- `project/source-recovery.json` 与 `input/`、`route.json` 一致（如果
  `recovery_required=true`）；控制器在 `frozen_delivery` 中会拒绝缺少该文件的交付；

### 3.2 SVC-EXPLOIT

重点看 `host_type` 是否真的落实：

| `host_type` | 审查重点 |
|---|---|
| `native_service` | 真的启动了上游 daemon/listener；正常协议客户端可用；不是只开端口 |
| `real_host` | 真的构建并运行真实应用；请求沿真实调用链进入受影响组件 |
| `synthetic_host` | 薄而忠实的公开 API 适配器；有真实协议/权限/会话/状态/网络边界；host 代码不直接实现漏洞效果 |

额外检查：

- `exploit.py` 在 verifier 新建的**独立 runner 容器**（固定使用 `images.agent`）
  中运行，只通过 `client:port` 交互；
- oracle 判定目标侧效果，不信任提交 stdout/退出码/HTTP 200；
- vulnerable/fixed 使用同一份 host/runner/oracle 代码；
- 只有 crash、ASan、单次 500、连接中断 → blocker（应走 FILE-POV）；
- 编译型 solution 必须替换实际加载的 binary/library 并重启。

### 3.3 FILE-EXPLOIT

重点看“一个文件 → 真实 release runner → 未授权效果”：

- 攻击文件由真实 CLI/公开 API runner 处理，不是只触发 crash；
- 效果是代码执行/受保护数据读取/未授权写入，不是任意非零退出；
- 同一文件、同一 runner 在 vulnerable/fixed 上做差分；
- 良性文件对照通过；
- `public_runner` 不存在（它只属于 FILE-POV）；
- oracle 不绑定 gold 的 marker/token/payload；
- 如果实际只能做 crash → blocker（应走 FILE-POV）。

### 3.4 FILE-POV

重点看“一个文件 + 固定 public runner → 精确故障”：

- `public_runner` 带 `{input}`，`runner.command=[]`；
- `gold/input.bin` 是数据，不是代码；
- oracle 检查**精确**的 sanitizer/runtime/resource 效果：
  - ASan/UBSan 错误类型 + 受影响函数/栈 + 分配区域；
  - 或其他语言对应的运行时故障；
  - 资源类要有有界指标和等预算对照；
- 任意非零退出、任意 assert/异常、泛泛超时都不算；
- 已修复版本上同一输入不触发；良性文件正常；
- **oracle 不能绑定 gold 输入的具体 size/offset/marker**；换一个同样触发漏洞的输入也必须得分；
- 审查时应尽量构造第二个形状不同的输入复测，不能只跑 gold；
- 编译型 solution 必须离线重建并替换实际 binary，保留 sanitizer。

## 4. “不要改交付”在 prompt 里说清楚了吗？

现在说清楚了，而且控制器会兜底。

审查 prompt 开头现在是：

> READ-ONLY REVIEW: do not create, modify, delete or chmod anything under
> delivery/. The controller re-hashes delivery after the review and rejects
> any change. Write only review.json in the workspace root.

控制器在 `pipeline/run.py` 里用哈希清单做两次检查：

1. 审查前记录 `frozen_inventory(delivery)`，审查后重新计算；新增、删除、改名、
   内容或大小变化、symlink 指向变化都会让两个字典不相等，直接报
   `independent review modified the submitted delivery`；
2. 审查通过后记录 `approved = frozen_inventory(delivery)`，Harbor 验收结束再
   `assert_frozen(delivery, approved)`，确认验收过程本身也没改交付。

哈希清单记录每个文件的相对路径、大小、sha256 和 symlink 目标，并排除
`.git`、`.agent-tmp`、`__pycache__`、`.pytest_cache`（否则审查里跑一次
`git status` 就会误报）。它不记录权限位，所以单纯的 `chmod` 不会被这份
检查发现。

任何被发现的修改都会让当前任务变成 `error`，不会进入 Harbor。

之前 prompt 只在末尾有一句 “Do not edit delivery”，不够醒目；现在把它提到
开头。

## 5. 审查输出

审查 Agent 只写：

```json
{
  "passed": true,
  "evidence": "oracle reads the target access log; vulnerable 200 / fixed 403 reproduced; healthcheck passed as uid 65534"
}
```

- 只允许两个字段；
- `passed` 是布尔；
- `evidence` 是非空字符串，写清文件、命令、观察到的行为；
- 不再有 `findings`、`reason`、`execution_checked`；
- 旧的四种字段只在 resume/re-review 旧交付时兼容读取，新审查不会再生成。

---

## 6. 审查预算

默认 `--review-turns 140`、`--review-timeout 5400`（90 分钟）。Prompt 要求
第 70 轮停止重复检查，第 100 轮前给出结论；额外预算用于 §3.1 的 agent 可见
捷径检查，而不是反复读同一批文件。

---

## 7. 一句话总结

审查 Agent 直接读取 `workspace/delivery/`，以及 `review-input/` 里的合成轨迹和
原始 fix.diff；它可以在宿主机上做只读检查，但不能修改交付，也不能代替 Harbor
跑完整差分。三个分支的检查重点不同，但共同底线是：**证据真实、效果精确、
vulnerable/fixed 同一路径、oracle 不绑定 gold、交付不可改。**
