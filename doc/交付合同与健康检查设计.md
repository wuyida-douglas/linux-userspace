# 交付合同、Compose 与健康检查

> 适用版本：2026-11-10 当前工作区。
> 本文解释两个容易混淆的设计：为什么还保留 `task.json`，以及
> `delivery/private/healthcheck.sh` 与 `task.json.healthcheck` 的分工。

## 1. Compose 和 task.json 的分工

### Compose 负责什么

`delivery/environment/docker-compose.yaml` 是**运行时拓扑**：

- `main`：分析工作站；
- `client`：漏洞目标；
- 其他服务：真实 sidecar，例如 DB、mock 服务；
- 每个服务的 image、command、healthcheck、depends_on、volumes。

对于 sidecar，导出器本来就是从 Compose 解析镜像：

```python
for name, service in public["services"].items():
    if name in {"main", "client"}:
        continue
    archive_image(service["image"], images / f"{name}.tar.gz")
```

因此 `task.json.images` **不包含 sidecar 镜像**。多容器题只写：

```json
{
  "images": {
    "agent": "analysis-agent:1",
    "target": "app-target:1"
  },
  "target_service": "client",
  "sidecar_services": ["db"]
}
```

Compose 里：

```yaml
services:
  main:
    image: analysis-agent:1
  client:
    image: app-target:1
  db:
    image: mysql:8.0
```

导出会得到：

```text
images/target.tar.gz
images/db.tar.gz
```

### task.json 负责什么

`delivery/task.json` 是**冻结的交付合同**，不是 Compose 的重复文件。它记录：

- `branch` / `host_type`：决定 SVC/FILE 语义；
- `images.agent` / `images.target`：导出和 verifier 的精确 tag；
- `interaction` / `submission_mode`：提交物是什么、怎么交互；
- `runner`：不可信提交执行器的 uid、超时；镜像固定复用 `images.agent`；
- `oracle` / `solution`：私有评分脚本入口；
- `public_runner`：FILE-POV 的真实执行器，来源是 Compose `client.x-public-runner`；
- `restart_command` / `runner_network_aliases`：仅为旧交付保留，新交付固定 `[]`；
- `sidecar_services`：哪些 Compose 服务是 sidecar。

### 为什么不能完全从 Compose 取

1. **main.image 不是最终 main 镜像来源**

   导出时 `harbor.py` 会删除 public Compose 的 main.image：

   ```python
   public["services"]["main"].pop("image", None)
   ```

   Harbor 最终使用 `task.toml` 的：

   ```toml
   [environment]
   docker_image = "<task.json.images.agent>"
   ```

   所以 `images.agent` 必须由合成阶段显式声明，不能从导出后的 Compose 推导。

2. **Compose 不知道“角色”**

   Compose 只知道三个服务都叫 `image: xxx`，不知道：

   ```text
   哪个是 target，哪个是 sidecar
   哪个是参考解、oracle、solution
   哪个是 runner，uid/超时是多少
   提交物是 exploit.py 还是 input.bin
   ```

3. **verifier 需要独立合同**

   最终 verifier 和 Harbor 的 private profile 只依赖冻结的 `task.json`，
   不需要重新解释一份可能被改写的 Compose。

4. **精确 tag 用于 docker save**

   导出按 `task.json.images` 的精确 tag 保存镜像。Compose 里的
   `:latest`、共享 tag 或多个服务共用镜像时，不能可靠判断交付物。

### 现在的实现：agent 不写 task.json

从 2026-11-10 起，合成 Agent **不再创建或编辑 `delivery/task.json`**。控制器
在冻结前调用 `pipeline.contract_build.build_task_contract()` 生成它：

- branch/host_type：来自 `workspace/route.json`；
- `images.agent` / `images.target`：来自公开 Compose 的 main/client；
- `sidecar_services`：来自 Compose 除 main/client 外的服务；
- `interaction` / `submission_mode`：按 branch 派生；
- `healthcheck`：按 branch 派生（见下一节）；
- `oracle` / `solution`：固定 `/private/*.sh`；
- `runner`：`image` 固定 `null`（复用 `images.agent`）；新交付用默认
  `65534:65534`/300 秒，旧交付 resume 时保留已冻结的 timeout/command；
- `restart_command` / `runner_network_aliases`：新交付固定为 `[]`，旧交付
  resume 时保留已冻结值；
- `public_runner`：FILE-POV 从公开 Compose 的 `client.x-public-runner` 读取。

FILE-POV 在 Compose 的 client 服务上声明：

```yaml
services:
  client:
    image: mytask-client:1
    x-public-runner:
      argv: ["/usr/local/bin/pov-runner.sh", "{input}"]
```

`x-public-runner` 只允许出现在 FILE-POV 的 client 服务上；控制器把它写进生成的
`task.json.public_runner`，并在导出的 Compose 中删掉这个扩展字段。SVC/FILE-EXPLOIT
不能有。

旧交付没有 `x-public-runner` 时，`build_task_contract()` 只从已冻结的
`task.json.public_runner` 读取兜底，保证 resume/re-review 仍可运行；新交付不允许
再手写 `task.json`。

生成后的 `task.json` 被冻结、哈希，review/export/verifier 只读它。

所以 `task.json` 没有消失，但不再是 agent 手写的第二份真相；它变成了从
Compose/route/脚本生成的构建产物。

## 2. healthcheck：脚本与执行契约

### 两个东西分别是什么

- `delivery/private/healthcheck.sh`：**脚本本体**，题目专属的正常功能探针。
  每道题必须有，`frozen_delivery()` 会检查。
- `task.json.healthcheck`：**执行契约**，告诉 verifier 执行哪个 argv、超时多少。

它们不是两个不同的检查。

### SVC-EXPLOIT / FILE-EXPLOIT

verifier 把 `delivery/private/healthcheck.sh` 复制成：

```text
harbor/verification/work/runner/public_healthcheck.sh
```

再挂到 runner 容器的 `/healthcheck.sh`，然后执行：

```text
runner /opt/pass2fail/runner.py --health
  -> task.json.healthcheck.argv
  -> /healthcheck.sh
```

所以 SVC/FILE-EXPLOIT 的 healthcheck 是从 **runner 镜像**（固定
`images.agent`，即 main 镜像）出发，以 uid 65534 向 `client` 发正常请求。
它不能依赖只在 target/client 镜像里存在的 `node`、`probe.mjs` 或其它工具。

绝对路径示例：

```text
/nvme/wuyida/新管线开发/results/iterate-20261109-08/batch-001/
  cve-2020-11002-svc-exploit-real-host/workspace/delivery/private/healthcheck.sh
```

### FILE-POV

FILE-POV 的提交是数据，healthcheck 在 client 里执行：verifier 把同一份
`private/healthcheck.sh` 挂到 client 的 `/healthcheck.sh`，然后执行：

```text
client /healthcheck.sh
```

绝对路径示例：

```text
/nvme/wuyida/新管线开发/results/iterate-20261109-08/batch-001/
  cve-2016-5844-file-pov/workspace/delivery/private/healthcheck.sh
```

### 现在的默认路径

从 2026-11-10 起，所有分支统一为：

```json
{"argv": ["/healthcheck.sh"]}
```

旧交付里的 `/opt/healthcheck/check.sh` 和 `/private/healthcheck.sh` 仍能读取
（resume 兼容）；冻结/规范化时会迁移成 `/healthcheck.sh`。

对应实现：

- `pipeline/task_contract.py:load_task()`：缺失时补默认；
- `pipeline/task_contract.py:normalize_declared_metadata()`：冻结前统一为
  `/healthcheck.sh`；
- `pipeline/prompts.py` 和各分支文档不再要求 agent 写 `healthcheck` 字段。

脚本本体仍然必须存在：

```text
delivery/private/healthcheck.sh
```

执行位置与责任的完整说明见
[healthcheck执行位置与责任](healthcheck执行位置与责任.md)。

## 3. Compose 无法表达的字段

### `restart_command`（仅旧交付）

fixed 阶段执行顺序：

```text
solution.sh 应用官方修复并重启服务
  -> patched healthcheck
  -> 再用同一份 submission 跑 fixed
```

对于常驻 daemon，`solution.sh` 可能只替换了磁盘上的 binary/library，但进程
仍然加载着旧代码。`solution.sh` 必须在内部重启服务，确保 fixed 阶段真的运行
修复后的程序。

`restart_command` 字段仍被 verifier 兼容读取，但只用于旧交付；新交付把重启
逻辑写进 `solution.sh`，不再暴露这个配置。旧交付示例：

```json
"restart_command": ["/usr/local/bin/restart-ftpd.sh"]
```

### `public_runner`

只用于 FILE-POV。它告诉 verifier：把 `input.bin` 放到 client 后，用哪个
真实 CLI/runner 执行。

例子，libarchive：

```text
/nvme/wuyida/新管线开发/results/iterate-20261109-08/batch-001/
  cve-2016-5844-file-pov/workspace/delivery/environment/docker-compose.yaml
```

```yaml
services:
  client:
    image: mytask-client:1
    x-public-runner:
      argv: ["/usr/local/bin/pov-runner.sh", "{input}"]
```

verifier 把 `{input}` 替换成上传后的 input 文件路径，再在 client 执行：

```text
/usr/local/bin/pov-runner.sh /run/pass2fail/input.bin
```

不同题的真实 runner 不同，所以不能从 Compose 的 `client.command` 推导。

### `runner_network_aliases`

给不可信 runner 额外加 DNS 别名，让 target 应用看到它期望的主机名。

例子，osquery：

```text
/nvme/wuyida/新管线开发/results/iterate-20261109-08/batch-001/
  cve-2020-26273-svc-exploit-native-service/workspace/delivery/task.json
```

```json
"runner_network_aliases": ["fleet-mgmt"]
```

应用配置里可能写死了 `fleet-mgmt` 这个管理端主机名，但 Compose 服务名是
`runner`。verifier 在 runner 网络上加 alias，使协议请求仍能到达预期目标。
没有这种需求时写 `[]`；大部分题都是空数组。

### `target_service`

当前合同固定：

```text
target_service = "client"
```

sidecar 是“除 main/client 以外的所有 Compose 服务”，由
`sidecar_services` 描述。因此“哪个是 target”确实可以约定为 client，
`target_service` 字段可以从 agent 的输入里省略，由管线默认。

它保留在验证器合同里，是为了让 standalone verifier 不必重新解释 Compose。
未来如果完全生成 `task.json`，这个字段可以直接写成常量。

## 4. task.toml 是怎么生成的

`task.toml` **不是 agent 写的**，也不在 `delivery/` 里。它由
`pipeline/harbor.py` 在导出时生成：

```python
# pipeline/harbor.py
TASK_TOML = '''version = "1.0"
artifacts = ["/workspace/{submission}"]
...
[metadata]
task_id = "{task_id}"
branch = "{branch}"
...
[environment]
docker_image = "{agent_image}"
...
'''

def export(delivery, destination, task_id, route, agent_image=None, ...):
    contract = load_task(delivery / "task.json")
    agent_image = agent_image or contract["images"]["agent"]
    public = read_public_compose(delivery, contract)
    profile = destination / "harbor-runtime-profile"
    (profile / "task.toml").write_text(TASK_TOML.format(
        submission=contract["submission_mode"],
        task_id=task_id,
        branch=contract["branch"],
        host_type=contract.get("host_type") or "none",
        interaction=contract["interaction"],
        agent_image=agent_image,
        verifier_image=VERIFIER_IMAGE), encoding="utf-8")
```

生成位置：

```text
<acceptance>/bundle/<delivery_id>/harbor-runtime-profile/task.toml
```

字段来源：

| task.toml 字段 | 来源 |
|---|---|
| `artifacts` | `task.json.submission_mode`（FILE-POV 是 input.bin，其他是 exploit.py） |
| `task.name` / `metadata.task_id` | 导出题名 |
| `metadata.branch` / `host_type` / `interaction` | `task.json` |
| `metadata.submission_mode` | `task.json.submission_mode` |
| `[verifier.environment].docker_image` | 公共 `linux-userspace-verifier:22.04` |
| `[environment].docker_image` | `task.json.images.agent`，即 main 分析镜像 |

之后 `copy_environment()` 会：

```python
public["services"]["main"].pop("image", None)
```

把 main.image 从公开 Compose 删除，因为 Harbor 用
`[environment].docker_image` 注入 main 镜像。target/client 镜像仍来自
Compose 的 `client.image`，并由导出器单独打成 `target.tar.gz`。
