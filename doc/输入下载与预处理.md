# 输入下载与预处理：从候选池到 Agent 工作区

> 本文描述当前代码的实际行为，权威实现为 `pipeline/prepare.py`、
> `pipeline/run.py` 和 `pipeline/common.py`。运行命令见根目录 `README.md`。
> 文档编辑不启动下载、模型或合成任务。

## 1. 预处理完全由脚本完成

`python -m pipeline.prepare` 是确定性的 Python 数据准备程序，不调用模型。
它完成固定抽样（或全量准备）、S3 定点下载、候选匹配、格式/完整性检查、
精简元数据、本地清单和错误回执。`python -m pipeline.run` 在每题工作区创建
时复制输入，并补充备用候选索引。源码恢复、补丁语义核验和分支判断才由
后续 Agent 完成。

数据准备是**分支无关**的：SVC-EXPLOIT、FILE-EXPLOIT、FILE-POV 共用同一份
`input/`。分支选择只发生在路由阶段，不在下载阶段预先分类。

必须区分三个层次：

| 层次 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| 下载/缓存完整性 | 对象存在，字节数和本地文件摘要符合记录 | 源码一定属于正确漏洞版本 |
| 输入格式 | 元数据可解析，源码非空，补丁有 Git diff 头，symlink 不逃逸 | diff 一定是该 CVE 的真实安全修复 |
| 路由与合成验证 | 核实真实 vulnerable/fixed、可达性和漏洞差分 | 尚未运行的题不能预先视为通过 |

`manifest.json.status=complete` 只代表前两层。它不表示漏洞真实性、构建、
独立审查或 Harbor 已通过。

## 2. 输入不是直接从整个 S3 bucket 复制

### 2.1 固定候选池

默认生产候选池是经过 S3 可用性过滤的派生文件：

```text
data/frozen-pool-20261109/candidates-kept-available-20261109.jsonl
```

原始 LLM 打标输出保留为 `data/frozen-pool-20261109/candidates-kept.jsonl`
（23,873 行，SHA-256 `1d9bdbd0…6142`），仅用于审计。过滤报告见
`data/frozen-pool-20261109/pool-availability-20261109.json`，被移除的行见
`removed-rows-20261109.jsonl`。

程序在任何 S3 调用之前强制检查：

- SHA-256 为 `565bdf5914152b3a4f2a00f44c09cc85a38f1b85ae8d42bb833a72c38579e941`；
- 恰好 22,138 行，且 `instance_id` 唯一；
- 每行 `metadata_label.label == keep`。

候选池生成/过滤脚本用于构造/审计候选集合，不是每次运行生产管线都要重新
筛选。不要为了补数量而重排池、修改 seed 或挑选容易成功的实例。需要新候选
池时，必须另建池和样本并重新记录其 provenance。

### 2.1.1 S3 可用性过滤（`scripts/filter_pool_by_s3.py`）

过滤只移除**确认无法下载**的行，不按“看起来容易”筛选：

- 既没有 `osv_<canonical_id>` / `cvelist_<canonical_id>`，也没有任何生态
  别名目录（如 `osv_UBUNTU-CVE-...`）；
- 别名目录存在，但其 `meta.json` 没有与该行 candidate 匹配的候选。

23,873 → 22,138 的结果：

```text
保留                                  22,138
移除                                   1,735
  ├─ 完全没有 exact/alias 目录          1,730
  └─ 别名目录不含该 candidate               5
其中通过生态别名恢复                      601
```

复现命令：

```bash
.venv/bin/python scripts/filter_pool_by_s3.py \
  --input data/frozen-pool-20261109/candidates-kept.jsonl \
  --output data/frozen-pool-20261109/candidates-kept-available-20261109.jsonl \
  --removed data/frozen-pool-20261109/removed-rows-20261109.jsonl \
  --report data/frozen-pool-20261109/pool-availability-20261109.json \
  --workers 20
```

可选 `--s3-listing <file>` 复用缓存的顶层 `rclone lsf` 输出。

过滤不保证剩余每一行都能逐字节下载成功（例如镜像对象损坏仍会失败）；
它只移除系统性的“目录根本不存在”缺口。

### 2.2 默认先抽样；scale-up 用 `--all`

`sample()` 按候选池原有行序执行：

```python
random.Random(seed).sample(rows, count)
```

每条抽样记录 `selection.jsonl` 保留任务位置、实例身份、仓库、漏洞信息、
候选 commit 列表和旧标签。任务 ID 中的 `linux-NNN` 是固定样本位置，不是
漏洞编号或成功序号。

`sample.json` 记录 seed、数量、候选池路径/摘要和抽样策略。后续重复执行
不会重新随机抽题；已有 `selection.jsonl` 的数量不同会直接报错。

任务 ID 由 `common.task_id()` 生成，格式为：

```text
linux-<样本位置:03d>-<canonical_id>-<owner-repo>
```

例如 `linux-014-cve-2024-23346-materialsproject-pymatgen`。它**不再把
`https://github.com/...` 整段 URL 塞进名字**；只保留仓库 owner 和仓库名，
既短又能区分同名仓库。样本位置编号保证同一池内唯一。

### 2.3 全量模式（scale-up）

`--all` 按冻结池的原始行序准备全部 22,138 条，不做随机抽样：

```bash
# 一键入口（推荐）
scripts/prepare_full_pool.sh samples/full-20261109 30

# 等价原生命令
.venv/bin/python -m pipeline.prepare \
  --input data/frozen-pool-20261109/candidates-kept-available-20261109.jsonl \
  --output samples/full-20261109 \
  --all --workers 30
```

规则：

- `--all` 与 `--count` 互斥；`--all` 也不能和 `--top-up-from` 混用；
- `sample.json.sampling_policy` 写为 `all(frozen_pool_order)`；
- 已有 `selection.jsonl` 时只校验 `instance_id` 顺序与冻结池完全一致，
  然后补齐/复核缺失下载，可安全重复执行；
- 仍支持 `--sample-only` 只生成清单，以及 `--only` 修复指定位置；
- 全量会下载所有源码快照和 `fix.diff`，运行前确认磁盘、S3 配额和并发
  （`--workers` 最大 30）。

## 3. 每个实例如何找到 S3 对象

默认 remote 前缀：

```text
p_huawei_hdd1:private-data-3/DataWheel/en-code-osv-nvd/file
```

只探测该 CVE 的已知来源，按 `osv`、抽样记录 `source_hint`、`cvelist`，
最后是生态别名目录的顺序尝试；重复来源不重复访问。元数据路径是：

```text
<remote>/<source>_<canonical_id>/meta.json
<remote>/osv_<VENDOR>-<canonical_id>/meta.json   # 仅当裸 CVE 目录缺失
```

`prepare.py` 启动时会做一次**顶层**目录列表
（`rclone lsf --dirs-only --max-depth 1`）建立 CVE → 别名目录索引，例如
`osv_UBUNTU-CVE-2022-37315`。它不会递归 list 整个 bucket，也不会对九万条
前缀逐个 copy。某个来源失败会保留错误，继续有限的已知来源探测；所有来源
均无可用对象时该位置记为 `error`。

命中的实际目录会写入 `input/meta.json.source_path`，例如
`osv_UBUNTU-CVE-2022-37315`；`source` 仍记作 `osv`，便于审计走了哪个别名。

### 3.1 候选 commit 的匹配

下载的 `meta.json` 可能含多个 candidate。选择顺序为：

1. `candidate_id` 与抽样记录完全一致；
2. 若找不到，选择同一规范化仓库、且 prefix/fix revision 都存在的候选。

规范化仓库由 `repository_key()` 处理协议、末尾斜杠、`.git` 等表示差异。
第二种是明确的 `same-upstream-snapshot-fallback`，不是无约束选择最新代码。
最终 `meta.json` 同时保存实际 `candidate_id` 和目录中的 `catalog_candidate_id`，
可以审计是否发生 fallback。

这是元数据匹配规则，不是补丁语义证明。如果 commit 映射错误，后续必须
恢复真实修复及其漏洞父版本，不能隐瞒或改写原始证据。

### 3.2 只下载选定 candidate 的证据

对象布局：

```text
<remote>/<source>_<CVE>/meta.json
<remote>/<source>_<CVE>/candidates/<candidate_id>/prefix/
<remote>/<source>_<CVE>/candidates/<candidate_id>/fix.diff

# 生态别名（仅当裸 CVE 目录不存在）
<remote>/osv_<VENDOR>-<CVE>/meta.json
<remote>/osv_<VENDOR>-<CVE>/candidates/<candidate_id>/prefix/
<remote>/osv_<VENDOR>-<CVE>/candidates/<candidate_id>/fix.diff
```

只拉 `prefix/` 和 `fix.diff`，不拉 `base/`、`fix/`、`.git/` 或其他候选。
`prefix/` 复制到 `input/src/`，`fix.diff` 原样复制到 `input/fix.diff`。
不会把补丁预先打进漏洞源码。

## 4. 下载完整性怎样检查

### 4.1 目录对象

`copy(..., directory=True)` 先列举该 candidate 下的文件和字节数，然后定点
并发复制，再逐文件核对：

- 本地必须存在且为普通文件，不是 symlink；
- 本地字节数必须与远端一致；
- 少文件、截断或异常对象名都会报错。

对 S3/rclone 递归处理有兼容问题的“路径段以点结尾”对象，使用精确对象
GET。普通文件下载也不只相信 rclone 退出码：核对远端 `Content-Length` 和
实际写入字节数，再原子 rename 到目标位置。

这些逻辑是为可审计地下载证据服务，不应由 Agent 在运行中重新实现。

### 4.2 staging 与缓存

新任务先写入同目录的 `.staging-*`，完成检查和清单后才 rename 为正式
任务目录。失败时删除暂存，不把空目录误标为可运行输入；原始错误写入
`download-report.json` 和 `download-history.jsonl`。

已有任务再次执行时，排除 `manifest.json` 自身，重新计算其余文件的
字节数和 SHA-256，并与清单逐项比较。文件集合或摘要不一致即
`integrity_ok=false`，拒绝把该缓存当成完整证据。完整缓存不会为了“试试看”
重新换一份上游代码。

缺 `fix.diff` 的旧缓存可以按已保存的 candidate provenance 定点补拉；
补拉后重新生成清单。`recovered_late_patch`/`repaired` 用于区分后续补齐和
首次下载完整，不能改写成首次即完整。补齐同样只证明格式和完整性。

## 5. “剔除冗余元数据”具体指什么

准确说是**按固定白名单重建顶层 `meta.json`**，不是 Agent 自己判断，也不是
把所有大字段递归删除。当前保留的顶层字段为：

| 字段 | 用途 |
| --- | --- |
| `instance_id` | 全链路不可改写的实例身份 |
| `cve` / `repo` | CVE 与上游仓库线索 |
| `candidate_id` / `catalog_candidate_id` | 实际候选与目录候选的对应关系 |
| `candidate_selection` | 精确匹配还是同仓库 fallback |
| `source` | 实际使用的 OSV/CVEList 来源 |
| `vulnerability` | 漏洞描述、CWE、引用等合成线索 |
| `candidate` | 所选 prefix/fix、来源及 revision 证据 |
| `old_tags` | 仅供路由参考的历史标签，不能当真实性标签 |

不自动复制远端 `meta.json` 的其他顶层字段，例如与当前题无关的完整抓取
上下文、其他来源的冗余索引等。当前实现**不会递归裁剪**保留对象内部所有
数组：`vulnerability` 和选中的 `candidate` 仍按证据保留；因此 Prompt 还要求
只读取需要的字段，不打印完整 affected-version 数组。这是上下文预算约束，
不改变磁盘上的原始证据。

随后脚本检查：

- `input/src/` 至少有一个文件；
- symlink 不能是绝对路径，也不能解析到源码目录之外；
- `fix.diff` 若存在，至少包含 `diff --git a/... b/...` 行；
- 缺补丁记 `partial`，不是静默当作无补丁可用；
- 空/缺失元数据、无有效候选、空源码、损坏下载、非法 symlink 均保留错误。

## 6. `alternate-candidates.json` 是何时生成的

它不是 S3 的原始文件，也不是下载补丁时生成的替代补丁。

每题首次创建工作区时，管线将只读输入从：

```text
samples/<sample>/tasks/<task-id>/input/
```

复制到：

```text
results/<run>/<task-id>/workspace/input/
```

然后 `write_candidate_leads()` 根据该样本的 `selection.jsonl` 写入：

```json
{
  "alternate_candidates": [
    {
      "candidate_id": "...",
      "origin_url": "...",
      "prefix": "候选漏洞版本 revision",
      "fix": "候选修复 revision",
      "source_references": []
    }
  ],
  "advisory_reference_urls": ["..."]
}
```

它排除当前选中的 candidate，仅保留其他候选的少量定位字段，以及最多
30 条 advisory URL。用途是给源码/补丁恢复提供线索；这些 revision 仍需
官方上游核验。原始 `input/src/` 和 `input/fix.diff` 不会被这个步骤替换。

## 7. 预处理后的目录和状态

```text
samples/<sample>/
├── sample.json                  # 固定池、seed、抽样策略（随机或 all）与数量证明
├── selection.jsonl              # 固定位置与恢复线索，不随成功失败重排
├── download-report.json         # 本轮每位置状态与错误
├── download-history.jsonl       # 保留下载历史
└── tasks/<task-id>/
    ├── task.json                # task/instance 与输入状态
    └── input/
        ├── src/                 # 所选 prefix 快照，未自动打补丁
        ├── fix.diff             # 所选候选补丁，可缺失
        ├── meta.json            # 白名单重建的精简证据
        └── manifest.json        # 文件集合、字节数、SHA-256、状态

results/<run>/<task-id>/workspace/input/
└── alternate-candidates.json    # 运行准备时生成的备用定位索引
```

- `complete`：源码和补丁通过上述格式/完整性检查，可以进入合成调度。
- `partial`：当前实现通常表示缺补丁；固定严格生产批次不能悄悄把它当作
  `complete`，应保留位置并明确处理。
- `error`：元数据/源码不可用、下载失败、缓存不一致等。保留原始 S3 错误，
  归类 `input_unavailable`，不派遣合成 Agent，不自动换一个新 CVE。
- `cached`：本次使用已存在缓存，仍须通过清单比对。

`--top-up-from` 是另一种明确的新样本策略：保留已有完整输入、排除历史失败，
再抽取不同实例补齐。它会改变样本组成，不能与“固定 100 个原始位置”的
严格实验口径混用。普通 `pipeline.run`/`pipeline.supervise` 当前没有统一的
`manifest.status == complete` 入口校验；严格固定样本的协调路径通过
`--preserve-unavailable-inputs` 做此检查。工程 scaling 前应把该校验前置到
所有生产入口，不能依赖 Agent 发现输入缺失。

## 8. Agent 与管线的职责边界

预处理脚本负责：身份、定点下载、完整性、格式、只读输入和恢复线索。
路由 Agent 负责：从候选证据提出可验证分支，不因证据缺失直接拒绝。
合成 Agent 负责：必要时从官方上游找回真实源码和修复，记录
`delivery/project/source-recovery.json`，构建 vulnerable/fixed 对照。
独立审查和 Harbor 负责：核验交付与真实差分，不相信 Agent 自述成功。

## 9. 与 exploit 管线的对应关系

exploit 管线按 CVE 将 S3 的现成 `{source}_{CVE}/` 目录拉到 `DATA_ROOT`，
从 `data/meta.exploit.g0.jsonl` 取对应行，写成该目录下的
`meta.exploit.json`。候选目录已经有 `prefix/` 和 `fix.diff`，不需要新管线
这种“固定池随机抽样 + 候选匹配 + 白名单 meta + 备用索引”的流程。

两者共同点：都不要整桶下载；都保留原始 prefix/fix 证据；都不能把“文件
下载成功”当作“漏洞修复语义正确”。新管线的额外步骤是为了可复现的固定
样本、跨来源 candidate 对齐、不可变输入和逐位置失败归因。
